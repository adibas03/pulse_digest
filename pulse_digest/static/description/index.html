Pulse — Daily Exception Digest

Find what needs attention across Accounting and Sales, on the schedule you set. Pulse lists the actual records to act on — not just counts — with statistical anomaly detection for the outliers a fixed threshold misses.

Records, not counts

A KPI summary tells you that twelve invoices are overdue. Acting on it means opening a list view, sorting it, and working out which twelve. Pulse sends the twelve: each one named, linked, ranked by amount, scoped to the person who owns it.

Six detectors included

Each detector is enabled or disabled per company, with its thresholds overridable from the configuration screen. Statistical detectors need a few weeks of history before they are useful, so they ship switched off.

How it works

You choose the hour the digest goes out, and each company chooses its own. Set it for the start of the working day, for the hour before a standup, or for the end of the afternoon — whatever matches when someone will actually act on it.

Behind that, a single scheduled action serves every company: each configuration decides for itself whether it is due, against its own run hour in its own timezone. Companies in different regions each get their digest at the right local time, with no extra scheduled actions to create and nothing to maintain as you add companies.

Audience

  • Company-wide — one digest covering everything, sent to a chosen list of recipients.
  • Per-user — each recipient receives only the records they own, resolved from the salesperson or invoicing-user field on each record.
  • Both — managers get the full picture, individuals get their own.

Delivery

Email and in-app notification. A channel reaches a recipient only when the company configuration allows it and that person has it enabled in their own preferences, so nobody is subscribed to a channel they did not ask for.

Writing your own detector

A detector is a plain Python class. There is no UI builder to buy and no scripting layer to learn: subclass the base, yield findings, and register one catalog record. The whole framework is LGPL-3. 

from odoo.addons.pulse_digest.models.constants import SEVERITY_WARNING
from odoo.addons.pulse_digest.models.detectors.base import (
    PulseDetectorBase, PulseFinding,
)


class LowStockDetector(PulseDetectorBase):
    TECHNICAL_NAME = "stock.low_on_hand"
    DEFAULT_PARAMS = {"min_qty": 5.0}

    def compute(self, env, scope):
        domain = [
            ("qty_available", "<", self.params["min_qty"]),
            ("company_id", "=", scope.company.id),
        ]
        for product in env["product.product"].search(domain):
            yield PulseFinding(
                res_model="product.product",
                res_id=product.id,
                res_name=product.display_name,
                summary=f"{product.display_name}: {product.qty_available} on hand",
                severity=SEVERITY_WARNING,
            )

Add one pulse.detector record pointing at the class and it appears in the configuration screen alongside the built-in six, with the same enable/disable and parameter-override behaviour. Detectors declare the modules they depend on and stay hidden when those are not installed, so a detector written against Inventory causes no trouble on a database without it.

Good to know

Every finding is delivered on every run. This release has no recurrence back-off: an invoice that stays overdue appears in tomorrow's digest too. Showing a problem again is recoverable; hiding one quietly is not, so the safe behaviour ships first. Scheduled for a later release.

Statistical detectors need history. Payment Delay Outliers and Deal Velocity Drop compare against a rolling per-customer or per-salesperson baseline. On a new database they find nothing until there is enough data, which is why both ship disabled.

Per-user digests follow record ownership. A record with no assigned user cannot be routed to anyone, so it appears in the company-wide digest only. Running both audiences is the recommended setup.
